# CyberPi LEDs, Ultrasonic Sensor 2 LEDs, Quad RGB Sensor: Live Mode API

Research date: 2026-10-02. Context: expressions are sent over BLE as one Python expression (f3 frame, mode=1) and evaluated on the robot with `cyberpi` and `mbot2` in scope; the reply is `{"ret": value}` (see 01-ble-protocol.md §4).

Legend: every claim carries a source. **UNVERIFIED** = inferred, or documented but not confirmed on hardware by any source I could inspect. "HW-verified" = a source states it was run on a real mBot2.

## B. Ultrasonic Sensor 2 LEDs (8 blue)

**Namespace**: `cyberpi.ultrasonic2` (HW-verified: [DS] commit a2077db, "`mbot2.ultrasonic2.get(1)` doesn't exist (returned None). The real namespace is cyberpi.ultrasonic2"; commands.md:68-73). [MB] also uses `cyberpi.ultrasonic2.*` (table:294-299). Uploaded on-robot programs use `mbuild.ultrasonic2` ([PX] 01-Ultrasonic Sensor2/*.py); whether `mbuild` is in scope in Live Mode is **UNVERIFIED**. [RV] protocol.rs:141 uses `mbot2.ultrasonic2.get(1)`, which [DS] found wrong.

**Colour**: blue only, 8 LEDs, brightness-controlled ([DOC-U] "equipped with eight blue LEDs ... programming their brightness"; [DS] sensors.md:86). No colour API exists in any source.

**`index`** = which Ultrasonic Sensor 2 on the mBuild chain, default 1 ([DOC]: every call has `index=1`; [MB] api:956-975). Always 1 for a stock mBot2.

**LED numbering** ([DOC] figure "LEDs and their numbers", attachment 20073389064343): 4 LEDs around each transducer. Eye A: 1 = outer side, 2 = top, 3 = inner side, 4 = bottom; eye B: 5 = top-inner, 6 = top-outer, 7 = outer side, 8 = bottom-inner (positions read from an angled exploded drawing, approximate). Which eye is the robot's left vs right is **UNVERIFIED**; [DS] reports left/right appears mirrored relative to the viewer (sensors.md:124-125). [DOC-U] example: "smiling" = LEDs 1, 2, 5, 6 on and 3, 4, 7, 8 off, i.e. 1,2,5,6 are the upper arcs.

Interpretation: the live `cyberpi.ultrasonic2` object appears to be a lower-level driver whose `set_bri`/`led_show` differ from the documented ones. [DS] did not record trying the documented 2/3-arg forms (`set_bri(100, 3, 1)`, `led_show([..8..], 1)`), so whether they work is **UNVERIFIED**. Per-LED control is therefore the biggest open question; test order:
1. `dir(cyberpi.ultrasonic2)`
2. `cyberpi.ultrasonic2.set_bri(100, 1, 1)` (documented per-LED)
3. `cyberpi.ultrasonic2.led_show([100,100,0,0,100,100,0,0], 1)` (documented list form)
4. fallback: `[cyberpi.ultrasonic2.set_both_led_bri(100,0), cyberpi.ultrasonic2.led_show()]` ([DS] form, one round trip via a list expression)

## C. Quad RGB Sensor (bottom)

**Namespace**: `cyberpi.quad_rgb_sensor` (HW-verified [DS] sensors.md:183-194; [MB] table:274-293). Uploaded programs use `mbuild.quad_rgb_sensor` ([PX]).

**Probe IDs (`ch`)**: int 1-4 or string `"L2"/"L1"/"R1"/"R2"` (lower case also accepted); some calls also take `"any"` ([DOC]). Physical order left to right, looking in the direction of travel: **L2 L1 R1 R2 = ch 4 3 2 1** (ch 1 is the rightmost). Source: [LB] ("beginnt rechts mit der Zahl 1 und endet beim linken Sensor mit 4"); consistent with [DOC] listing `"L2"/"L1"/"R1"/"R2"/.../4/3/2/1` in parallel. Not HW-verified by me.

**`index`** = which Quad RGB Sensor on the mBuild chain, default 1 ([DOC], [MB]). Always 1 on a stock mBot2.

### C4. Polling cost and batching

- In [MB], the sensor reads (`get_line_sta`, `get_offset_track`, `is_line`, `is_background`, `is_color`, `get_gray`, `get_color`, `get_color_sta`, `get_light`) use `get_value`, which **subscribes** (`subscribe.add_item(key, func, params)`, modules.py:82-86, 132-149) so the robot pushes updates; `get_red/green/blue` use a plain request (api:909-917). This implies Makeblock treats the first group as cheap, continuously-updated readings. The subscribe push protocol over BLE is **UNVERIFIED** and not needed: plain eval polling at 2-5 Hz is a small number of BLE round trips.
- **No single call returns all four probes** in any source. Instead, batch with a list expression. `[cyberpi.quad_rgb_sensor.get_gray(i) for i in (1,2,3,4)]` is **HW-verified** by [DS] sensors.md:194. By the same mechanism, mixed lists such as `[q.get_line_sta(1), ...]` should work; use **lists, not tuples**, because the reply is JSON-ish and MicroPython prints tuples as `(..)` (01-ble-protocol.md §4 on lenient parsing).
- Live Mode evaluates one expression; a name binding like `q = cyberpi.quad_rgb_sensor` is a statement and is not available (unless wrapped in `exec`), so spell out the full path. Reply size: a 16-int list is about 60-80 bytes, fine within one or two BLE notifications. **UNVERIFIED** latency; measure.
- Suggested 2-5 Hz poll (one round trip): see table below. `get_color_sta` x4 makes the sensor run colour detection and change fill lights ([DOC] note), so poll colour names at a lower rate or on demand. **UNVERIFIED** per-read cost on the device.
